# 问题一 V0 接手审计与 V1-lite 判断

本地工作副本从 `main` 的 `eb64420ae9b4cc1dcf80cc7fc4824fac8db0f614` 建立 `q1-v1` 分支。官方附件已放入 Git 忽略的 `data/raw/A题附件/`。哈希检查全部一致，原有 15 项测试通过。使用已提交的 V0 方案重新运行官方评估器，`case_093 K=3` 得 25103、`case_026 K=2` 得 101996、`case_025 K=2` 得 2431840、`case_014 K=5` 得 18174673 cycles，均与结果表吻合。V0 的合法性与可复现性可信；这不等于性能代理精确或结果最优。

结构审计给出更具体的原因。`case_093` 有 69 个独立计算分量，V0 的 K=3 恰好分成三个可并行块，而 K=4 的最优候选却切为 32 块、只用两个核心，边界 COPY 增至 561152 bytes。`case_026` 有 31 个分量，其中最大分量占 40824/111760 工作周期；K=2 的 V0 两块全落一个核心，多核反而增加 COPY 和等待。`case_025` 有 2666 个小分量，K=5 时只有两个核心工作，速度停在约 2 倍。`case_014` 有 1340 个分量，K=5 的 40 块仍全部放在一个核心，并新增 85156672 bytes COPY，其中 22258080 bytes 是 spill。连续等工作量切分破坏了分支边界，随后即时 EFT 分核无法恢复已失去的并行性。

因此先改分块，再检验分核。V1-P 保留连续拓扑区间的无环性质，比较确定性、关键路径优先、分支连续三种拓扑序；切点同时考虑工作量、张量大小、依赖条数、扇出和关键路径。张量搬运按官方 Task 边界规则逐 Tensor 计数。V1-S 对每个可选核心做一步试分配，并用剩余块的贪心补全预测全局 Makespan；空闲核心仅在预测值接近最优时获得有限优先。新增 `src/q1/partition_v1.py`、`schedule_v1.py`、`experiments_v1.py` 与测试，V0 入口保持可运行。每个消融版本最多送 4 个候选给官方评估器。

仍需用更多用例判断：分支连续顺序是否普遍有效、增加的 COPY 会否抵消并行收益、V1-S 是否有独立贡献，以及大图评价耗时能否支持全部 100 例。正式平均效果须以全量固定配置的官方评估结果为准。
